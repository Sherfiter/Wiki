# 第 2 章 · 应用层

浏览器里按 F12 打开 Network 面板,刷新页面,你会看到一列请求。随便点一个,右侧有 Headers、Cookies、Timing 几个标签,HTTP 的请求、响应、耗时全部摊开在这里。我最早是盯着面板里的一个 `301` 发呆:明明访问的是一个网址,列表里却先出现一条旧地址的请求、再出现一条新地址的。后来才明白重定向是服务器下发的指令,浏览器只是照办。应用层协议就这么大点事:两端约定好消息长什么样,剩下的交给下层。

## 2.1 HTTP:请求与响应长什么样

HTTP 是无状态的请求-响应协议:客户端发请求,服务器回响应,一来一回,服务器默认不记得你是谁(所以才有 Cookie 这类补丁)。报文是纯文本,人能直接读。对 `http://info.cern.ch` 发一个请求,响应头是真实长这样(我用 `curl -I` 抓的):

```
HTTP/1.1 200 OK
Date: Sat, 24 Oct 2026 13:29:06 GMT
Server: Apache
Last-Modified: Wed, 05 Feb 2014 16:00:31 GMT
ETag: "286-4f1aadb3105c0"
Content-Length: 646
Connection: close
```

结构上,第一行是状态行(版本 + 状态码 + 原因短语),往下是首部字段的键值对,空一行,再是响应体。请求报文对称:第一行是请求行(方法 + 路径 + 版本),往下同样是首部。`curl -v http://info.cern.ch` 发出的请求(节选)是:

```
> GET / HTTP/1.1
> Host: info.cern.ch
> User-Agent: curl/8.23.0
> Accept: */*
>
```

请求行、首部、空行,POST 的话再往后是请求体。`Host` 这个字段是 HTTP/1.1 才强制加上的:一台服务器一个 IP 上挂几百个域名,全靠它区分你到底要哪个站。没有它,虚拟主机托管这件事就不成立。

首部里几个字段值得认识:`Content-Length` 告诉你响应体多长(对端按这个数读,读够为止),`Last-Modified` 和 `ETag` 服务缓存协商(下一条 304 会用到),`Connection: close` 说的是用完这条 TCP 连接就关(2.3 节细说)。

## 2.2 方法、幂等与状态码

常用方法五个:GET(取)、POST(交)、PUT(整体替换)、DELETE(删)、HEAD(只要首部不要体)。比背方法更重要的是「幂等」这个性质:同一个请求执行一次和执行一百次,服务器状态的结果相同。GET、PUT、DELETE 幂等,POST 不幂等(连发两次就是两条资源)。

这个性质有实际用途。网络里请求超时太常见,客户端需要重发,而只有幂等的操作才能放心重发;你的转账接口若是 POST 且不做幂等键,网络抖一下就可能扣两次款。写接口时先想幂等,这是 HTTP 语义送给你的免费设计约束。

状态码三位数,首位定类:2xx 成功(200 OK、201 Created、204 No Content),3xx 重定向,4xx 客户端的锅(400 参数错、401 未认证、403 禁止、404 找不到),5xx 服务器的锅(500 内部错误、502 网关收到的上游响应不合法、503 暂时不可用)。排查问题先看这一位,就知道该去查前端还是后端。

HEAD 是个不起眼但顺手的方法:语义和 GET 完全一致,只是服务器不返回正文。下载一个大文件前先 `curl -I` 一下,看 `Content-Length` 再决定要不要下,就是它的典型用法。

3xx 里三个值得区分:301 永久移动(浏览器会缓存,以后直接去新地址),302 临时移动(每次都先问旧地址),304 Not Modified(资源没变,配合 2.1 节的 `ETag`/`Last-Modified`,服务器让你用本地缓存,正文都不用传)。

## 2.3 HTTP 的三个版本,以及它们各自头疼的事

HTTP/1.0 每个请求都要新建一条 TCP 连接,握手开销全额支付。HTTP/1.1 引入持久连接(keep-alive),一条连接上可以排队发多个请求,但队列是串行的:第一个请求没回来,后面的只能等,这叫队头阻塞。HTTP/2 用二进制分帧 + 多路复用解决连接内排队,多个请求在同一连接上并发交错。不过队头阻塞只是被推到了更低的层,TCP 层丢一个包,所有流都得等它重传,这个问题要到 HTTP/3 换掉 TCP 才根治(第 3 章讲完 UDP 你就明白它为什么能这么干)。

## 2.4 DNS:人记域名,机器认 IP

网络层只认 IP(第 5 章),所以域名必须先翻译成 IP,这件事由域名系统(DNS)完成。DNS 本质是一棵分层的分布式数据库:根(`.`)→ 顶级域(`.com` 等)→ 权威服务器(`example.com` 的 DNS 服务器)。本机查一个域名,在我机器上的真实输出:

```
$ getent hosts example.com
2606:4700:10::ac42:93f3 example.com
2606:4700:10::6814:179a example.com
```

(域名常配多个地址,顺序和内容随地点、时间变,这也意味着「一台网站服务器」往往是一批。)

完整流程值得走一遍:先查本机缓存和 hosts 文件;未命中,问「本地 DNS 服务器」(你的路由器或运营商的递归服务器);它没有缓存的话,替你从根开始一路问下去。这里有个常被考混的区分:客户端到本地服务器是递归查询,「你替我查到底,我只等结果」;本地服务器到根、顶级域、权威是迭代查询,每级只回答「下一步去问谁」,查的是接力赛。现实中两者混合:你递归,它迭代。

DNS 响应里每个记录带 TTL(秒),缓存到期就得重查。所以新域名解析全球生效要等 TTL 过期,改 DNS 配置后「怎么还没生效」,九成是缓存没到 TTL。

## 2.5 邮件与 DHCP:两个老协议,快速过

这两个协议工程上你大概率不会手写,但考试常客,各用几行说清。

邮件分发送和收取两条链路。SMTP(端口 25,提交常用 587/465)是推协议,客户端把信推给自己的服务器,服务器之间再一跳跳推到收件方的服务器;收信是拉,POP3(110/995)把信下载到本机、默认下载后删除,IMAP(143/993)则让邮件留在服务器上,多设备同步靠它。你手机和电脑同时能看到同一封邮件,是 IMAP 的功劳。

DHCP 解决的是新设备接入时的鸡生蛋问题:一台笔记本刚连上 Wi-Fi,连 IP 都没有,怎么跟服务器通信。答案是四步广播:DISCOVER(大声问,有 DHCP 服务器吗)、OFFER(某台服务器提议一个 IP)、REQUEST(客户端广播「我就要这个」,注意仍是广播,让其他出了 OFFER 的服务器死心)、ACK(成交,附带子网掩码、网关、DNS、租期)。全程 UDP,谁都没 IP 的时候只能靠广播,这是它能跑起来的前提。

## 练习

1. 打开 DevTools 的 Network 面板刷新本页,找出一条 304 或 200 的请求,对照 2.1 节读它的响应头;如果有 304,想想服务器是根据哪个首部判断资源没变的。
2. 手算:一个页面引用了 30 个资源,HTTP/1.0、HTTP/1.1(持久连接、串行)、HTTP/2 各需要付出几次队头等待?说说三者排队的位置有何不同。
3. 思考:`dig +trace example.com` 会从根服务器开始一级级打印解析过程。跑一下(或看截图),指出哪一步是递归、哪一步是迭代。
4. 思考:为什么 DHCP 的 REQUEST 要用广播,而不是单播给选中那台服务器?
