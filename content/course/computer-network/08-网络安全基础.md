# 第 8 章 · 网络安全基础

前面几章都在「把数据送到」，这一章讨论「怎么安全地送」——安全是**横切所有层**的问题（物理层的窃听、链路层的伪造、网络层的欺骗、应用层的入侵）。核心四件事：**机密性（加密）、完整性（签名）、身份认证（证书）、以及它们如何组合成 TLS/HTTPS。**

## 8.1 对称加密 vs 非对称加密

> 对比：**对称加密**用同一把密钥加密和解密，**快**但密钥分发难；**非对称加密**用一对公钥/私钥，公钥加密私钥解、私钥签名公钥验，**解决了密钥分发**但**慢**（是前者的上千倍）。

| 维度 | 对称加密 | 非对称加密 |
|---|---|---|
| 密钥 | 一把，双方共享 | 一对（公钥 + 私钥） |
| 速度 | 快 | 慢（数学运算昂贵） |
| 密钥分发 | 难（如何安全共享） | 易（公钥可公开） |
| 典型算法 | AES、ChaCha20 | RSA、ECC（如 ECDSA） |
| 用途 | 加密大量数据 | 密钥交换、数字签名 |

所以实践中**混合使用**：用非对称加密安全地协商出一把对称密钥（会话密钥），再用对称加密传输大数据——TLS 正是这么干的。

## 8.2 数字签名与证书

**数字签名**：发送方用**私钥**对消息的哈希加密，接收方用**公钥**解密验证。它提供**完整性**（内容没被篡改）和**不可否认性**（确实是私钥持有者发的），但不提供机密性。

**证书**：解决「公钥是谁的」这个信任问题。证书 = 公钥 + 持有者信息 + **CA（证书颁发机构）的签名**。浏览器内置了受信任 CA 的公钥，用来验证服务器证书的签名，从而**信任链**成立（CA 签服务器证书，根 CA 自签）。

## 8.3 TLS 握手

TLS 在 TCP 之上（见第 4 章）、HTTP 之下，用一次握手协商出会话密钥。简化流程（TLS 1.2 RSA）：

```
客户端                                 服务器
  │ ── ClientHello（支持的版本/算法/随机数）──→ │
  │ ←─ ServerHello + 证书 + 随机数 ────────── │
  │ 验证证书 → 生成 PreMaster，用公钥加密 ────→ │
  │         双方用 随机数+PreMaster 派生会话密钥│
  │ ←────────  Finished（对称加密开始）────→  │
```

- **握手阶段用非对称加密**（密钥交换 + 认证），**数据传输阶段用对称加密**（性能）。
- TLS 1.3 进一步精简：握手从 2-RTT 降到 **1-RTT**（甚至 0-RTT 恢复），并淘汰了 RSA 密钥交换，改用 ECDHE 提供**前向保密**。

## 8.4 HTTP vs HTTPS

> 对比：**HTTPS = HTTP + TLS。** 它补上了 HTTP 的三大短板：**机密性（明文变密文）、完整性（防篡改）、身份认证（防中间人）。**

| 维度 | HTTP | HTTPS |
|---|---|---|
| 默认端口 | 80 | 443 |
| 加密 | 明文传输 | TLS 加密 |
| 身份认证 | 无 | 服务器证书 |
| 中间人攻击 | 易受 | 可防 |
| 性能 | 略快（无握手开销） | 握手 + 加密有开销（TLS1.3/HTTP2 已大幅缓解） |
| 适用 | 非敏感内容 | 登录、支付等一切敏感内容 |

> 承上启下：TLS 工作在应用层（HTTP）与传输层（TCP，见第 3、4 章）之间，是「横切层」的典型。第 10 章完整旅程里，HTTPS 请求会在 TCP 建连后、HTTP 发送前插入一次 TLS 握手。
