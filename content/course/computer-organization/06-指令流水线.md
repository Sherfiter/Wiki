# 第 6 章 · 指令流水线

第 5 章的单周期/多周期都在「一条指令独占机器」里打转。流水线的洞见：**把指令执行拆成若干独立阶段，让不同指令同时处于不同阶段**，像工厂流水线一样——周期还是那么短（多周期的优点），但吞吐逼近 1 IPC（单周期的理想）。代价是引入了三类「冒险」，本章逐个拆解。

## 6.1 五级流水线

经典 RISC 五级（MIPS 教科书标准）：

```text
IF → ID → EX → MEM → WB
取指  译码  执行  访存  写回
```

| 级 | 缩写 | 干什么 |
|---|---|---|
| 取指 | IF | PC 取指令到 IR，PC+1（或 +4） |
| 译码/读寄存器 | ID | 译 opcode，读 rs1/rs2，符号扩展立即数 |
| 执行 | EX | ALU 运算 / 算有效地址 |
| 访存 | MEM | 仅 load/store 用，读写数据内存 |
| 写回 | WB | 结果写回寄存器文件 |

```text
周期:    1     2     3     4     5     6     7     8
指令1   IF    ID    EX    MEM   WB
指令2         IF    ID    EX    MEM   WB
指令3               IF    ID    EX    MEM   WB
指令4                     IF    ID    EX    MEM   WB
```

**稳态时每个周期完成一条指令**（IPC≈1），五条指令同时在场，各占一级。总时间 ≈ (k + n - 1) 个周期（k 级、n 条指令），比单周期 k×n 快近 k 倍。

> 对比：性能三重奏——**单周期**周期长、吞吐 1；**多周期**周期短但吞吐 1/k；**流水线**周期短且吞吐≈1。流水线的本质是**「把关键路径切成 k 段，每段配一级锁存器，让硬件并行忙碌」**，牺牲的是锁存器面积和「冒险」带来的停顿。

## 6.2 三类冒险（Hazard）

流水线要求「每条指令的语义与顺序执行完全一致」，违反就是冒险：

### 结构冒险（structural）
两条指令**同时要用同一个硬件资源**，硬件不够用。典型：单存储器机器里 IF 取指和 MEM 访存同时访问内存。解法：**分离指令/数据 Cache（第 1 章哈佛思想在 Cache 层落地）**、寄存器文件做成「前半个周期写 + 后半个周期读」、加多端口。

### 数据冒险（data）
后一条指令要用前一条**还没写回**的结果。分三种：

| 类型 | 含义 | 危险 |
|---|---|---|
| RAW | 读后写（真依赖） | 后读旧值，必须处理 |
| WAR | 写后读（反依赖） | 顺序执行不出现，乱序才出现 |
| WAW | 写后写（输出依赖） | 同上，乱序才出现 |

顺序流水线里只需处理 **RAW**（WAR/WAW 是乱序执行第 8 章的课题）。RAW 的典型：

```x86asm
add r1, r2, r3   ; r1 在 EX 算出，WB 才写回
sub r4, r1, r5   ; ID 阶段就要读 r1 —— 但 r1 还没写回！
```

### 控制冒险（control）
分支/jump 会改写 PC，但**取指在分支结果算出来之前就要决定下一条取哪**。解法：分支预测（6.4）。

## 6.3 转发（Forwarding）与停顿（Stall）

**转发（旁路 bypassing）**：数据在 ALU 一算出来、还没写回寄存器时，就**直接从 EX/MEM 或 MEM/WB 级间锁存器「偷」出来**，绕过寄存器文件直接喂给下一条的 EX 输入。解决大多数 RAW，几乎零代价。

```text
add r1, r2, r3    EX 算出 r1 ──┐
sub r4, r1, r5    EX 需要 r1 ◄─┘ 直接旁路，不经过 WB
```

**停顿（stall / 插入气泡）**：有些 RAW 转发救不了——最典型是 **load-use**：

```x86asm
ld  r1, 0(r2)    ; r1 要到 MEM 结束才知道
add r3, r1, r4   ; EX 就需要 r1，转发也来不及
```

这时必须在流水线里**插入一个气泡（bubble）**，让 `add` 等一个周期。编译器会**指令调度**：把无关指令塞进 load 和 use 之间，尽量填掉这个气泡。

> 对比：**转发 vs 停顿**——转发用「绕路」把数据提前送到，不损失吞吐；停顿用「等待」硬扛，损失一个周期。两者的取舍标准是「数据最早在流水线哪一级可用」：EX 之后可转发，load 的 MEM 阶段才可用就只能停。编译器 + 硬件联手，把停顿压缩到最少。

## 6.4 分支预测

控制冒险的解法，核心是「**赌一个方向，赌错了就冲刷**」。

**静态预测**：编译时定死——总是预测不跳（BTFN, back taken / forward not taken，循环往回跳就取）、或由编译器用 BTB 填提示位。

**动态预测**：运行时用历史。常用部件：

- **BTB（分支目标缓冲）**：记住「这条分支上次跳到哪」，命中就直接取目标地址。
- **两位饱和计数器**：00/01/10/11 四态，预测正确 +1、错误 -1，**连续错两次才翻转预测**——避免一次偶发跳变来回翻转（loop 里循环 100 次，只在进/出时错各一次）。

```text
        预测不跳           预测跳
           │  错        错  │
      ┌────┴──┐       ┌────┴──┐
  不跳 00 ──▶ 01      11 ◀── 10  跳
      ▲           ◀──正确──▶          ▲
      └──────── 连续错两次才跨越  ───────┘
```

> 注意：**预测错误的代价** = 冲刷已经进入 IF/ID/EX 的错误指令，损失 k 个周期（k≈流水线深度）。现代 CPU 用更深的流水线（十几级）换更高主频，代价就是预测错更贵，于是**分支预测器成了 CPU 性能的隐形发动机**——这也是为什么「CPU 漏洞（Spectre）能从分支预测器侧信道偷数据」。

## 6.5 与后续 / 语言对照

- **第 7 章 Cache**：结构冒险的解法（指令/数据 Cache 分离）同时是 Cache 层的设计；而 load 停顿的长短、预测错冲刷的代价，都受存储层次延迟支配——流水线和存储层次是绑定的。
- **第 8 章**：乱序执行才让 WAR/WAW 变成真问题，需要寄存器重命名（第 8 章/超标量的延伸）消解。
- **C/Java**：**分支预测对「有序数据的循环」极其友好**——`for` 循环里 `if` 条件稳定，预测率高；`if` 条件随机（如排序后二分查找）预测率崩到 50%，性能骤降。这是「同样 O(n) 的代码，实际快慢差几倍」的常见来源。

> 承上启下：**流水线用「分段并行」把吞吐做到 1 IPC，代价是三类冒险；转发治数据冒险，分支预测治控制冒险，Cache 分离治结构冒险——三者共同撑起现代 CPU 的性能。** 而「Cache 分离」已指向下一章：存储层次。
