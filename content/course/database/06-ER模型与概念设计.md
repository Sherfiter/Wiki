# 第 6 章 · ER 模型与概念设计

第 5 章讲「表怎么拆才规范」，但拆之前得先知道**现实世界有哪些东西、它们怎么联系**。ER 模型（实体-联系模型）就是做这件事的**概念工具**——它独立于任何具体 DBMS，先画清业务，再落到关系模式。

## 6.1 实体、属性、联系

- **实体（Entity）**：可区分的客观对象，如「学生张三」「课程数据库」。同类实体集合叫**实体集**（Student）。
- **属性（Attribute）**：实体的特征，如学生的学号、姓名。**码属性**（下划线标）唯一标识实体。
- **联系（Relationship）**：实体之间的关联，如「学生**选**课程」。联系也可以带属性（如选课联系的「成绩」）。

```
        ┌─────┐
        │学生 │──────── 选课 ────────┐
        └──┬──┘  (学号,姓名,年龄)     │
           │                          ▼
           │                      ┌──────┐
        ┌──▼──┐                   │课程  │
        │班级 │                   │(课号,课名)│
        └─────┘                   └──────┘
```

## 6.2 联系的基数：1:1 / 1:N / M:N

联系的**基数比**描述一个实体能关联多少个另一实体：

| 基数 | 含义 | 例 |
|---|---|---|
| 1:1 | 一对一 | 班级 ↔ 班长 |
| 1:N | 一对多 | 班级 → 学生 |
| M:N | 多对多 | 学生 ↔ 课程（选课） |

基数决定了后面「怎么落到表」：**1:1 和 1:N 可以只靠外码合并，M:N 必须单独建一张联系表。**

## 6.3 ER 图符号

- 矩形 = 实体集，椭圆 = 属性，菱形 = 联系。
- 联系两端标基数：`1`、`N`、`M`。
- 码属性名加**下划线**；多值属性用双椭圆；弱实体用双矩形。

画 ER 图的要点：**先找实体，再找实体间的联系，最后补属性**；联系是「动作」（选、属于、雇佣），不是名词。

## 6.4 ER 图到关系模式的转换规则

概念模型最终要变成第 2、5 章的关系模式，规则固定：

1. **每个实体集 → 一张表**，属性即列，码即主键。
2. **1:1 联系**：任选一端实体，把另一端的主键作为外码并入（联系自身的属性也一并放进去）。
3. **1:N 联系**：把「1」端主键作为外码并入「N」端表。
4. **M:N 联系**：**单独建一张联系表**，主键 = 两端主键的组合（`(学号, 课程号)`），联系属性（成绩）作为该表的列。

```
学生(学号 PK, 姓名, 班级号 FK)     ← 1:N：学生并入班级外码
课程(课号 PK, 课名)
选课(学号 FK, 课号 FK, 成绩)        ← M:N：单独建表，主键(学号,课号)
```

转完后的每张表，再用第 5 章的范式逐级验收、必要时拆分。

> 对比：概念 / 逻辑 / 物理三阶段——**概念设计**（ER 图）面向业务人员，谈「有哪些实体、怎么联系」，**完全不管实现**；**逻辑设计**（关系模式 + 范式）面向数据库设计者，把 ER 图翻译成表并规范化，**不管存储细节**；**物理设计**（索引、聚簇、分区，见第 9 章）面向具体 DBMS 和硬件，决定「数据怎么落在磁盘上」。三阶段是「业务 → 逻辑 → 物理」的逐层落地，每层都屏蔽下层细节，正是第 1 章三级模式思想在设计流程上的体现。

> 承上启下：本章补上了设计流程的「上游」——先有 ER 图，才有第 5 章的关系模式和范式验收；转出的表直接是第 3、4 章 SQL 操作的舞台。ER 图里「M:N 单独建表」的决定，正是第 4 章多表连接和第 9 章连接优化的源头。三阶段中「物理设计」的具体手段（索引怎么选）留待第 9 章展开。
