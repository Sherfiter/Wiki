# 第 9 章 · 索引与查询优化

前面八章让数据「能存、能查、能并发、能恢复」，但**快不快**取决于索引。本章讲 B+ 树与哈希两类索引、聚簇与覆盖索引、最左前缀，以及怎么用 `EXPLAIN` 看清查询在做什么。

## 9.1 为什么是索引

没有索引，DBMS 查一行只能**全表扫描**（O(n)）。索引是一种**辅助数据结构**，用额外的空间换查询时间，本质是「为数据建目录」。索引的选型直接决定第 4 章连接、第 5 章查询的性能。

## 9.2 B+ 树索引 vs 哈希索引

| 维度 | B+ 树索引 | 哈希索引 |
|---|---|---|
| 结构 | 多路平衡树，叶子层全链成有序链表 | 哈希表（桶 + 冲突链） |
| 等值查找 `=` | O(log n)，快 | O(1)，**更快** |
| 范围查找 `BETWEEN`/`>` | ✅ 叶子有序，顺序扫 | ❌ 不支持，只能全扫 |
| 排序 / 最左前缀 | ✅ | ❌ |
| 适用 | 默认首选，通用 | 仅等值、且无范围排序需求的场景 |

```
B+ 树（非叶子只存索引键，数据全在叶子）
        [ 10 | 20 ]
        /     |     \
    [5|8]  [12|15] [25|30]      ← 非叶子节点
      │       │       │
    叶子: 5→8→10→12→15→20→25→30   ← 叶子层有序双向链表
```

- B+ 树把**数据全部放在叶子层**、非叶子只做「路标」，叶子用链表串起来——所以既能等值也能范围。
- 树**矮而胖**（一个节点存几百个键），一次查找只需 2~4 次磁盘 IO，这正是它适合磁盘的原因。

> 对比：B+ 树 vs 哈希——**B+ 树**是「有序 + 支持范围」，是数据库默认索引，几乎万能；**哈希**在纯等值上更快（O(1) vs O(log n)），但**一旦要范围、排序、前缀匹配就失效**。选型规则：**有范围/排序/前缀需求就用 B+ 树；只有等值且无排序，才考虑哈希**（如内存数据库、等值 KV）。MySQL 的 Memory 引擎支持哈希，InnoDB 默认 B+ 树（也可建自适应哈希索引）。

## 9.3 聚簇索引 vs 非聚簇索引

| 维度 | 聚簇索引 | 非聚簇（二级）索引 |
|---|---|---|
| 叶子存什么 | **整行数据** | 索引键 + 主键值（指针） |
| 每表数量 | 只能 1 个 | 可多个 |
| 主键即聚簇 | 是（InnoDB） | — |
| 回表 | 无需 | 查到主键后再回聚簇索引取整行 |

**InnoDB 的主键索引就是聚簇索引**：数据按主键物理有序存储。二级索引（如对 `name` 建的索引）叶子存的是「name → 主键」，若还要别的列就得**回表**再查一次主键索引——这是额外的 IO。

## 9.4 联合索引与最左前缀

**联合索引**（复合索引）按多列建一棵 B+ 树，列顺序至关重要：

```sql
CREATE INDEX idx_dept_age ON student(dept, age);
```

索引按 `(dept, age)` 排序。**最左前缀原则**：查询只有从联合索引的**最左列**开始、按顺序命中，才能用上它：

```
WHERE dept = 'CS'                    ✅ 用上（最左列）
WHERE dept = 'CS' AND age > 20       ✅ 用上
WHERE age > 20                       ❌ 跳过 dept，用不上
WHERE dept = 'CS' AND age > 20 AND sname = 'x'  ✅ 前两列用上
```

所以建联合索引时，把**等值、区分度高、常用的列放最左**。列顺序不对，索引白建。

## 9.5 覆盖索引与执行计划

- **覆盖索引（covering index）**：查询需要的**所有列都在索引里**，就**不用回表**，一次索引扫描搞定，是最优形态。为此常把 `SELECT` 的列也加进联合索引。
- **`EXPLAIN`**：看一条 SQL 实际走了哪个索引、扫描多少行、是否回表：

```sql
EXPLAIN SELECT * FROM student WHERE dept = 'CS';
```

关键字段：`type`（访问方式，`const > ref > range > index > ALL`，`ALL` 是全表扫描=最差）、`key`（用到的索引）、`rows`（预估扫描行数）、`Extra`（`Using index` = 覆盖索引，`Using filesort` = 额外排序要警惕）。

> 对比：聚簇 vs 非聚簇——**聚簇索引**把数据和主键绑在一起物理存储，主键查询/范围极快且无回表，但只能有一个、插入时可能页分裂、主键要短且递增；**非聚簇索引**轻量、可建多个、不重排数据，但查到主键后**还要回表**取整行。二者配合的经典优化：**让二级索引「覆盖」查询列**（覆盖索引），既省回表、又保持主键聚簇有序。

> 承上启下：本章补齐了第 1 章「存储管理器」和「查询处理器」的落地——索引属于内模式，`EXPLAIN` 是查询优化的窗口。**连接**（第 4 章）快不快，看有没有合适的索引；**间隙锁/锁范围**（第 7 章）锁的就是索引记录；**B+ 树的页**与第 8 章的脏页刷盘、WAL 同属存储层。第 10 章对比 MySQL/PostgreSQL/MongoDB 时，各自「默认索引结构」的差异也由此而来。
