# 第 10 章 · 数据库对比与应用

前九章以「关系模型 + SQL + 事务/索引」为主线，讲的是**关系型数据库**的通用原理。但真实选型时，你要在 MySQL、PostgreSQL、Redis、MongoDB 之间做选择。本章把它们放到一起，并用前九章的概念作标尺——**选型不是背参数，而是认清「一致性 vs 扩展性」的取舍**（第 2 章埋的钩子在此收网）。

## 10.1 关系型 vs NoSQL 四大类

| 类型 | 代表 | 数据模型 | 一致性 | 横向扩展 |
|---|---|---|---|---|
| 关系型 | MySQL、PostgreSQL | 表 + 外键（第 2 章） | 强（ACID） | 难（分库分表） |
| KV 存储 | Redis | 键 → 值 | 弱/可配 | 易（分片） |
| 文档型 | MongoDB | JSON 文档（无固定模式） | 弱（可配） | 易（分片） |
| 列式 / 图 | HBase、Neo4j | 列族 / 图 | 不一 | 不一 |

NoSQL 的共同动机：**放弃部分关系代数能力（连接、强约束、跨行事务），换取水平扩展与高吞吐**。第 2 章说关系模型靠「值匹配 + 连接」表达复杂联系，NoSQL 恰恰是把这些昂贵能力砍掉，让单机/单分片内的操作变简单。

## 10.2 MySQL（InnoDB）vs PostgreSQL

| 维度 | MySQL（InnoDB） | PostgreSQL |
|---|---|---|
| 默认隔离级别 | REPEATABLE READ（靠 MVCC+间隙锁） | READ COMMITTED |
| 存储引擎 | InnoDB 单一主流 | 单一引擎，可扩展 |
| 索引 | 聚簇主键 + B+ 树（第 9 章） | 默认 B+ 树，非聚簇为主 |
| 并发 | MVCC + undo 版本链 | MVCC，多版本原地保留 |
| 扩展能力 | 复制成熟、分库分表生态大 | JSONB、窗口函数、可编程性强 |
| 事务 | 完整 ACID | 完整 ACID，隔离级别更全 |

**选型倾向**：MySQL 生态大、运维资料多、读多写少的 Web 场景顺手；PostgreSQL 标准更严、功能更强（窗口函数、CTE、JSONB、全文检索），适合对正确性和复杂查询要求高的场景。二者都是第 7、8 章「事务 + 日志」原理的忠实实现。

## 10.3 Redis：内存 KV

Redis 是**内存键值存储**，数据主要在 RAM，持久化靠 RDB 快照 + AOF 日志（近似第 8 章的 WAL 思想）。

- **强项**：微秒级延迟、丰富数据结构（String/List/Hash/Set/ZSet）、原子操作、发布订阅，常做**缓存、会话、计数器、排行榜**。
- **弱项**：内存容量有限、数据量大则成本高；持久化/复制是异步的，极端情况下可能丢最近数据——**不保证强一致**。

> 对比：Redis 的 AOF vs 关系库的 redo 日志——都是「追加写日志、崩溃后重放」，但 Redis 主要目标是**性能**，AOF 可配置为「每秒刷盘」甚至「不刷」，会牺牲持久性；关系库（第 8 章）用 WAL + 检查点把持久性做硬。**缓存可以丢一点，账本不能丢**——这正是选型时「一致性」权重的来源。

## 10.4 MongoDB：文档数据库

MongoDB 存 **BSON 文档**，无固定模式（schema-less），集合（collection）里文档结构可不同——与第 3 章「模式固定」的关系表相反。

- **强项**：嵌套文档免去多表连接（把第 4 章的 JOIN 换成「一个文档装下全部」）、模式灵活、天然分布式分片、适合**快速迭代、结构多变、写入量大**的场景。
- **弱项**：多文档跨集合事务近年才支持且代价高；没有真正的连接，复杂关系查询要手动聚合或反规范化（第 5 章的反规范化在 NoSQL 里成了常态）。

## 10.5 选型决策：回扣全课程

选型没有绝对答案，看你的**查询模式**落在前九章哪个维度上：

| 你的需求 | 指向 | 依据章节 |
|---|---|---|
| 强一致、复杂连接、严格事务 | 关系型（MySQL/PG） | 第 2、4、7、8 章 |
| 读多写少、能容忍短暂不一致 | MySQL + Redis 缓存 | 第 7 章隔离、第 9 章索引 |
| 结构多变、文档型、快速上线 | MongoDB | 第 5 章反规范化 |
| 热点数据、计数器、会话 | Redis | 第 9 章内存/哈希 |
| 复杂分析、报表、多维聚合 | 列式 / OLAP 引擎 | 第 5 章反规范化 + 第 4 章聚合 |

- **范式**（第 5 章）决定关系库的拆表；**反规范化**是 NoSQL 和 OLAP 的默认姿态——你是在「一致性」和「读性能」之间选边。
- **事务与隔离**（第 7 章）决定你能否接受「最终一致」：核心账务必须 ACID，浏览计数可以近似。
- **索引**（第 9 章）是无论选谁都绕不开的杠杆：Redis 用哈希结构、关系库用 B+ 树、MongoDB 也有自己的 B 树索引，**底层思想同源**。

> 对比（收束）：关系型 vs NoSQL——**关系型**用「表 + 连接 + 事务」换取**强一致与复杂查询能力**，代价是扩展难、模式僵；**NoSQL 四类**各自放弃一部分（连接、强事务、固定模式、磁盘持久化）换取**可扩展性与专项性能**。这不是「谁更好」，而是「你的数据长什么样、读多还是写多、能不能容忍不一致」。前九章讲透的是关系型的「完全体」，NoSQL 是它的**刻意裁剪**——理解了完全体，才知道每处裁剪丢掉的是什么。

> 承上启下（全课程闭环）：本章是终点，也是回望点。**第 2 章**的「关系 vs 非关系」钩子在这里收网；**第 3、4 章**的 SQL 与连接在关系库里是日常、在 MongoDB 里被文档嵌套替代；**第 5 章**的规范化与反规范化，直接决定你倾向关系库还是 NoSQL；**第 7、8 章**的事务与恢复，是「能不能用 Redis 当账本」的判据；**第 9 章**的索引思想贯穿所有库。选型 = 把前九章的知识，按你数据的「一致性需求 / 查询模式 / 扩展诉求」重新加权——数据库没有银弹，只有合适的取舍。
