# 第 8 章 · 故障恢复

第 7 章承诺了 ACID，但机器会崩。本章讲**崩了之后怎么把数据救回来**——核心是日志：先写日志、后写数据（WAL），再靠 undo/redo 双向修复。

## 8.1 三类故障

| 故障 | 影响范围 | 数据是否损坏 | 恢复手段 |
|---|---|---|---|
| **事务故障** | 单个事务（逻辑错/死锁被回滚） | 否，内存/未提交 | undo 回滚 |
| **系统故障** | 整个系统（掉电/崩溃） | 内存丢失，磁盘数据在 | redo + undo |
| **介质故障** | 磁盘损坏 | 是，数据真没了 | 备份 + redo 日志重放 |

区分关键：**前两类磁盘上的数据没丢**，只需让「已提交的重做、未提交的撤销」；介质故障数据真没了，得靠**备份副本 + 日志**。

## 8.2 日志：redo 与 undo

日志记录每个事务对数据的修改，两类用途相反的日志：

- **redo 日志（重做）**：记「改成了什么」（新值）。用于**重放已提交但还没落盘**的修改，保证持久性。
- **undo 日志（撤销）**：记「原来是什么」（旧值）。用于**回滚未提交**的修改，保证原子性。

```
事务 T：A = A - 100
redo 日志：<T, A, 新值>    → 崩溃后重做，把 A 写成新值
undo 日志：<T, A, 旧值>    → 回滚时撤销，把 A 写回旧值
```

> 对比：redo vs undo——**redo** 面向「已提交」，把数据库**向前推**到提交后的状态，解决持久性；**undo** 面向「未提交」，把数据库**向后拉**回事务前的状态，解决原子性。二者方向相反、用途互补：一次系统故障恢复 = **先 redo 所有已提交事务（防止已提交丢失），再 undo 所有未提交事务（清除半截修改）**。

## 8.3 WAL：先写日志再写数据

**WAL（Write-Ahead Logging，预写式日志）** 是恢复正确性的根基，规则就一条：

```
任何数据页落盘之前，它对应的日志必须先落盘（先写日志，后写数据）
```

为什么必须这样：数据页落盘后、日志还没写，此时崩溃 → 已提交的修改无法重做，持久性被破坏。WAL 保证**日志先于数据**，崩溃后总能从日志重建出正确状态。同时 WAL 把**随机写**（数据页）转成**顺序追加写**（日志），反而更快。

## 8.4 检查点（Checkpoint）

若每次恢复都从头扫全部日志，代价不可接受。**检查点**定期做三件事：

1. 把缓冲池里的**脏页刷盘**；
2. 在日志里写一条 `<CHECKPOINT>` 记录（含当时活跃事务清单）；
3. 恢复时**只需从最近检查点开始**，之前的要么已落盘、要么已确认。

```
时间轴： ... 检查点C1 ... 检查点C2 ... ─崩溃─▶ 恢复
恢复只需处理 C2 之后的事务，C2 之前已落盘
```

检查点越频繁，恢复越快，但正常运行的刷盘开销越大——又是一笔权衡。

## 8.5 恢复策略总览

- **事务故障**：用 undo 日志，把该事务改过的值逐个写回旧值（逆序）。
- **系统故障**：① **redo** 阶段——从最近检查点起，把已提交事务的重做日志重放；② **undo** 阶段——把未提交事务用 undo 逆序撤销。
- **介质故障**：先**装载最近完整备份**（冷备/热备），再**用 redo 日志重放**备份之后的所有已提交修改，补到崩溃点。

> 对比：三种故障的恢复手段——**事务故障**最轻，只在内存层 undo，速度快；**系统故障**磁盘完好，用「redo + undo」把库拉到一致状态，需扫最近检查点后的日志；**介质故障**最重，数据真没了，必须**备份 + 重放日志**才能还原，且备份间隔决定**数据丢失窗口（RPO）**。三者共同点：**都靠日志**——日志是恢复的唯一真相来源，这也是 WAL 和检查点如此重要的原因。

> 承上启下：本章兑现了第 7 章 ACID 的 **A（原子性，靠 undo）** 和 **D（持久性，靠 redo + WAL）**，两章合起来才是完整的事务引擎。**redo/undo 日志**与第 7 章的 MVCC 版本链、第 9 章的索引/B+ 树同处存储管理器（见第 1 章）——日志的写入顺序、脏页刷盘，都直接影响索引页与数据页的一致性。理解「日志先于数据」，第 10 章看 MySQL InnoDB 与 PostgreSQL 的 WAL 实现差异时就有了共同语言。
