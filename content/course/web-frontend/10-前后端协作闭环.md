# 第 10 章 · 前后端协作闭环

前 9 章都在浏览器里打转，这章把镜头拉远：前端发的每个请求（第 5 章的事件、第 7 章的 `fetch`）都要**穿过网络**抵达后端，后端**读写数据库**再把数据送回。理解这条链路，才算真正「闭环」。

## 10.1 前后端分离

传统服务端渲染：后端拼好 HTML 直接返回。现代**前后端分离**：前端只负责界面与交互，通过 **HTTP API** 向后端数据服务：

```
浏览器（前端 SPA，第 8 章框架构建）
   │  HTTP 请求（JSON）
   ▼
后端服务（API）
   │  SQL / ORM
   ▼
数据库（存用户、订单等）
```

- 好处：前端后端**独立开发、独立部署、独立扩容**，职责清晰。
- 代价：首屏要等 JS 加载再渲染（SPA），多一层网络往返，需配合 SSR/预渲染优化。

## 10.2 HTTP 与 REST API

前端用 `fetch` 走 HTTP（回扣「计算机网络」），REST 是主流 API 风格：

```js
fetch("/api/users/1", { method: "GET" })          // 查
fetch("/api/users", { method: "POST", body: JSON.stringify({ name: "Tom" }) })  // 增
fetch("/api/users/1", { method: "PUT", body: JSON.stringify({ name: "Jerry" }) })  // 改
fetch("/api/users/1", { method: "DELETE" })       // 删
```

| 方法 | 语义 | 幂等 |
|---|---|---|
| GET | 读资源 | 是 |
| POST | 创建资源 | 否 |
| PUT/PATCH | 整体/局部更新 | 是 |
| DELETE | 删除资源 | 是 |

- REST 用 **URL 表示资源、HTTP 方法表示操作**，返回 JSON；状态用 HTTP 状态码（200/400/401/404/500）表达。
- 幂等 = 重复执行不产生额外副作用（GET 重复读无害，POST 重复会插两条）。

> 对比：REST vs RPC——REST 面向**资源**（URL + 方法 + 状态码），语义统一、利于缓存和工具链；RPC 面向**动作**（`getUser(id)` 这样的过程调用），更贴合代码直觉、性能更细但耦合紧。对「资源型」业务 REST 更通用；内部服务间高频调用常选 RPC（gRPC）。

## 10.3 跨域 CORS

浏览器**同源策略**：协议 + 域名 + 端口都相同才「同源」。跨域请求会被浏览器拦截（是浏览器的限制，非服务器）：

```
前端 https://app.com  →  请求 https://api.com/user   ← 跨域
```

后端用 **CORS** 响应头放行：

```
Access-Control-Allow-Origin: https://app.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

- **简单请求**直接发，浏览器看响应头判断放行；**预检请求**（`OPTIONS`）先问一句「允许吗」再发真请求。
- 前端本地开发用 Vite 代理（第 9 章）把 `/api` 转发到后端，规避跨域。
- CORS 是「浏览器替用户把关」，**后端必须配合**；它防的是「别人网站冒用你登录态」，而非「阻止服务器收请求」。

## 10.4 鉴权：Cookie vs Token

**HTTP 无状态**，每次请求都要带身份凭证：

```http
# Cookie 方案：浏览器自动带上
GET /api/me
Cookie: session_id=abc123

# Token 方案：手动放请求头
GET /api/me
Authorization: Bearer eyJhbGciOi...
```

| | Cookie + Session | Token（JWT） |
|---|---|---|
| 存储 | 浏览器自动带 cookie | 前端显式存（localStorage/内存） |
| 状态 | 服务端存 session | 无状态，签名自包含 |
| 跨域 | 受同源策略限制 | 手动加 `Authorization`，跨域灵活 |
| 注销 | 服务端删 session 即失效 | 难立即失效（需黑名单/短过期） |

> 对比：Cookie vs Token——Cookie/Session 状态在服务端，安全可控但跨域麻烦、服务端要存状态；Token（JWT）无状态、天然适配前后端分离与跨域、易横向扩容，但泄露风险大、难以即时吊销。现代 SPA 多用 Token（配合 `HttpOnly` cookie 更安全），传统站点仍用 Session。

## 10.5 闭环：一条请求的完整旅程

把前面所有章节串成一条线：

1. 用户点击按钮 → **DOM 事件**（第 5 章）触发处理函数；
2. 函数里 `fetch`（第 7 章）发出 **HTTP 请求**，带上 Token；
3. 请求经 **DNS/TCP/TLS**（计算机网络）到达后端；
4. 后端验 Token → 查**数据库**（数据库课程）→ 返回 JSON；
5. 浏览器收到响应，更新**框架状态**（第 8 章），视图自动刷新；
6. 整个过程中，前端源码由 **git/npm/vite**（第 9 章）管理构建，浏览器按第 6 章的流水线渲染。

> 承上启下：这是课程终点——前端（1~9 章）是「界面与交互」，网络（HTTP）是「管道」，数据库是「记忆」，三者合起来才是一个能用的系统。前端只是入口，真正的业务价值在后端与数据；但**没有前端，用户就摸不到这一切**。学完这章，你应能独立打通「页面 → 请求 → 后端 → 数据库 → 回显」的完整闭环。
