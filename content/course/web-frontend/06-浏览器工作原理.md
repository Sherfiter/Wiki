# 第 6 章 · 浏览器工作原理

浏览器是前端代码的「运行时」。理解它如何把 HTML/CSS（第 1、2 章）解析成屏幕像素、如何加载脚本、如何发请求（回扣计算机网络），才能解释为什么「少动 DOM」（第 5 章）、「别用同步脚本」、以及页面为什么「白屏」。

## 6.1 渲染流水线

从输入字节到屏幕像素，主流程五步：

```
HTML ─解析→ DOM 树
CSS  ─解析→ CSSOM 树
           ↓ 合并
        渲染树（Render Tree）
           ↓
        布局 Layout（算每个盒子的几何位置，见第 2/3 章）
           ↓
        绘制 Paint（把盒子画成像素）
           ↓
        合成 Composite（分层合成上屏）
```

- **DOM 树**描述结构（第 5 章），**CSSOM**描述样式，两者合并成**渲染树**（只含可见节点，`display:none` 不进入）。
- **布局**计算元素尺寸位置（盒模型第 2 章、定位第 3 章在此生效），**绘制**填充像素。
- 现代浏览器还有**合成**：把页面分层（`transform`、`opacity` 触发 GPU 合成），改这些属性只重合成、不重排，动画最省。

## 6.2 回流 vs 重绘

| | 回流 Reflow | 重绘 Repaint |
|---|---|---|
| 触发 | 几何属性变化（尺寸/位置/内容） | 仅视觉属性变化（颜色/背景/阴影） |
| 代价 | 高（重新布局 + 可能重绘） | 较低（只重画像素） |
| 例子 | 改 `width`、增删 DOM、读 `offsetWidth` | 改 `color`、`background` |

```js
// 反例：读一次写一次，强制多次回流
for (let i = 0; i < 100; i++) {
  el.style.width = i + "px";     // 写 → 回流
  const w = el.offsetWidth;      // 读 → 强制同步回流
}

// 正例：用文档片段批量插入，只回流一次
const frag = document.createDocumentFragment();
for (let i = 0; i < 100; i++) {
  const node = document.createElement("div");
  frag.appendChild(node);
}
container.appendChild(frag);
```

> 对比：回流 vs 重绘——回流必然伴随重绘，重绘不一定回流。回流是「重新算几何」，重绘是「只重上色」，**回流的代价远高于重绘**。优化方向：批量修改 DOM、用 `documentFragment`、读写分离、动画只用 `transform/opacity`（走合成层，两者都不触发）。

## 6.3 JS 会阻塞渲染

HTML 解析遇到 `<script>` 会**停下解析，先下载并执行脚本**——因为脚本可能 `document.write` 改内容：

```html
<script src="app.js"></script>       <!-- 阻塞：下载 + 执行都卡解析 -->
<script src="a.js" defer></script>   <!-- 下载不阻塞，DOM 解析完再按序执行 -->
<script src="b.js" async></script>   <!-- 下载完立即执行，不保证顺序 -->
```

| | 阻塞解析 | 执行时机 | 顺序 |
|---|---|---|---|
| 普通 `<script>` | 是（下载+执行都卡） | 立即 | 按出现顺序 |
| `defer` | 否 | DOM 解析完成后 | 按出现顺序 |
| `async` | 否（下载时） | 下载完立即 | 不保证 |

> 对比：同步脚本 vs `defer`/`async`——同步脚本是「拦路虎」，把解析挡在身后，脚本大就白屏；`defer` 让脚本「晚点执行但保序」，适合依赖 DOM 的主脚本；`async` 让脚本「下载完就跑，不保序」，适合独立第三方脚本（统计、广告）。三者共用时 `async` 可能先于 `defer` 执行。

## 6.4 与网络请求的关系

页面渲染通常被**网络**卡脖子，而非 CPU：

1. 浏览器先发请求拿 HTML（DNS → TCP → TLS → HTTP，见「计算机网络」）；
2. 解析 HTML 时发现 `<link>`/`<script>`/`<img>`，再**并发**发起子资源请求（HTTP/1.1 每域名约 6 个并发，HTTP/2 多路复用）；
3. 关键资源（CSS、同步脚本）会阻塞首屏，所以要「内联首屏 CSS、`defer` 非关键脚本」。

- 浏览器有**缓存**：强缓存（`Cache-Control`）命中不请求，协商缓存（`ETag`/`Last-Modified`）命中少传体（见「计算机网络」的 HTTP 缓存）。
- 这正是第 9 章工程化的目标之一：打包压缩、代码分割、CDN，本质都是**减少网络往返、加快首屏**。

> 承上启下：本章把第 1~3 章的静态结构、第 5 章的 DOM 操作串成一条「解析→布局→绘制」的流水线，并解释了它们的性能成本；「JS 阻塞」「资源并发」则回扣计算机网络。下一章回到 JS 本身——ES6+ 语法、Promise/async、模块化、事件循环，它们决定代码怎么写、异步怎么编排，而事件循环正是浏览器「单线程却并发」的心脏。
