# 第 8 章 · 前端框架对比

当页面状态变多、交互变复杂，手写 DOM 操作（第 5 章）会变成不可维护的「意大利面条」。框架的价值是：**把「状态」和「视图」绑定起来，状态一变视图自动更新**，开发者只描述「状态长什么样」。Vue 和 React 是这条路上的两条主流路线。

## 8.1 组件化：复用与组合

两者都以**组件**为最小单元，组件 = 模板 + 逻辑 + 样式：

```js
// React：JSX，模板与逻辑都在 JS 里
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

```html
<!-- Vue：SFC 单文件组件，模板/脚本/样式分块 -->
<script setup>
import { ref } from "vue";
const count = ref(0);
</script>
<template>
  <button @click="count++">{{ count }}</button>
</template>
```

- 组件间靠 **props（父传子）+ 事件/回调（子传父）** 通信，跨层用状态管理（8.4）。

## 8.2 响应式：两条实现路线

这是两者最本质的分野：

- **Vue：依赖收集（细粒度）**。`ref`/`reactive` 把数据包成响应式对象，模板读取时**记录依赖**，数据变更时**精确通知**用到它的地方更新。
- **React：不可变数据 + 整树 diff**。状态更新靠 `setState` 返回**新对象**（旧的不动），然后**重渲染组件、比对虚拟 DOM**，算出最小变更再落到真 DOM。

```js
// Vue：直接改，自动追踪
state.count++;            // 依赖收集后精确触发

// React：不可变，必须用 setState 换新值
setCount(c => c + 1);     // 不直接改原值
```

> 对比：Vue 的依赖收集 vs React 的不可变 + diff——Vue 是「数据变了就知道谁该更新」的**细粒度**，理论上更新更精准；React 是「每次重渲染再 diff 出差异」的**粗粒度**，靠不可变数据保证 diff 高效（引用不等即变了）。Vue 心智更「自动」，React 心智更「显式」，但更可预测。

## 8.3 虚拟 DOM

两者都引入**虚拟 DOM（Virtual DOM）**：先在内存里的轻量对象树算出差异，再一次性提交给真 DOM，避免频繁触发第 6 章的回流/重绘：

```
状态变化 → 生成新 VDOM 树 → diff 出新旧差异 → 最小化 patch 到真 DOM
```

- 为什么要它：**批量化**、**跨平台**（VDOM 可渲染到 canvas/原生），且把「直接操作 DOM」的易错细节藏起来。
- Vue 的响应式让它只需重渲染「受影响组件」，React 则重渲染该组件子树再 diff。

## 8.4 状态管理

组件多了，跨组件共享状态要用集中式 store：

- React：`Redux`/`Zustand`/`Jotai`，核心是不可变 reducer + 单向数据流。
- Vue：`Pinia`（Vuex 的继任），利用响应式，改状态即同步视图。

| 维度 | Vue 3 | React |
|---|---|---|
| 模板 | 模板语法（更接近 HTML） | JSX（JS 内写标记） |
| 响应式 | 依赖收集（`ref`/`reactive`） | 不可变 + diff（`useState`） |
| 更新粒度 | 组件级精准 | 组件树重渲染 + diff |
| 状态管理 | Pinia | Redux/Zustand |
| 学习曲线 | 平缓 | 需适应 JSX/Hooks |
| 生态 | 官方全家桶（Router/Pinia） | 社区大而散 |

> 对比：Vue vs React 全面对照——Vue 上手平缓、模板直观、响应式自动，适合快速开发；React 心智模型统一（一切皆函数）、不可变数据可预测、生态庞大，适合大型复杂应用与跨端（React Native）。没有绝对优劣，**取决于团队习惯与项目规模**；两者都能胜任绝大多数业务。

> 承上启下：框架把第 4、7 章的 JS 能力组织成「状态→视图」的自动流水线，把第 5 章的手动 DOM、第 6 章的回流优化内化为虚拟 DOM 的批量提交。下一章进入工程化：git、npm、打包构建、部署，把这些「源码」变成可上线的产物。
